SKILLBRIDGE — PRODUCT UX, ONBOARDING, LEARNING, AND ASSESSMENT UPGRADE
Implementation guide for OpenCode

PURPOSE
---
Turn the existing SkillBridge application into a calm, high-end career-learning
product. The user should always understand: where they are, what a score means,
what to do next, and how to return later.

This is NOT a request to rebuild the app, replace the existing UI wholesale, or
invent mock functionality. Improve the current Professional and Casual Pulse
themes while preserving all existing routes, authentication, learning content,
practice, assessment, jobs, tutor, voice, and role features.

The design reference is the clarity and progression of products such as
TryHackMe, Hack The Box Academy, Duolingo, Linear, and Vercel. Do not copy their
screens, names, graphics, text, or branding. Build a recognizably SkillBridge
experience.

NON-NEGOTIABLE SAFETY AND DELIVERY RULES
---
1. Work from the current repository state. Do not restore, reset, overwrite, or
   replace existing source files with older copies.
2. Preserve all existing APIs, database data, .env files, provider settings,
   roles, accounts, and routes. Never print, commit, archive, or expose secrets.
3. Do not delete an existing feature merely because it is visually crowded.
   Use progressive disclosure: move secondary detail behind tabs, drawers,
   accordions, or "View details" controls.
4. Do not fake live jobs, assessment completion, verified skills, AI responses,
   provider health, or progress. Every new UI state must be backed by actual
   existing data or clearly labelled demo/empty state.
5. Do not add a paid dependency, external analytics, external jobs provider, or
   new AI/voice provider without an explicit user decision. Prefer existing
   dependencies and local code.
6. Maintain Professional light/dark and Casual Pulse light/dark themes. Do not
   hard-code colors where theme tokens can be used.
7. Preserve Arabic/RTL behavior. New UI must remain readable in English and
   Arabic, on desktop and mobile.
8. After EACH phase: run its tests, build, show what changed, list changed
   files, and STOP for approval. Do not continue automatically into the next
   phase.
9. Use small, cohesive commits. Never use a destructive git command.

PRODUCT PRINCIPLES (USE THESE IN EVERY PHASE)
---
1. One screen, one decision.
   Every primary screen has one clearly dominant action.
2. Progressive disclosure.
   Show the current task first. Show details only when requested.
3. Explain, do not merely score.
   Every percentage, match, and result must offer a short plain-language
   explanation and a useful next action.
4. Preserve user control.
   The user can skip tours, hide/reopen the mentor, return to a previous step,
   and manage preferences in Settings.
5. Calm before clever.
   Animation should orient or confirm, never distract. Avoid dashboards full of
   competing cards, badges, glowing effects, and calls to action.
6. Honest product behavior.
   If data is unavailable, explain why and give a retry/alternative action.

TARGET STUDENT JOURNEY
---
First login
  -> Welcome tour (optional)
  -> Choose or confirm target role
  -> Understand readiness / skill coverage
  -> Start diagnostic
  -> Receive a focused learning path
  -> Continue one lesson at a time
  -> Practice safely
  -> Take an assessment when ready
  -> Receive strengths, gaps, and an updated next step
  -> Explore relevant opportunities

The dashboard should be a launchpad, not a data warehouse. The system should
always highlight exactly one “next best action” based on real persisted state.

PHASE 0 — BASELINE, INVENTORY, AND QUALITY GUARDRAILS
---
Goal: Understand the current app before touching its UX.

Tasks:
- Read the current navigation shell, page components, theme preference code,
  role explorer, learning pages, assessment pages, tutor/mentor components,
  settings, and relevant API endpoints.
- Inventory all pages and make a short UX map: page purpose, primary action,
  supporting details, current empty/loading/error states, and mobile behavior.
- Run the existing frontend type check, production build, and relevant backend
  tests before changing code. Do not claim a baseline is green if it is not.
- Create a non-sensitive audit document at:
  docs/ux-upgrade/PHASE_0_BASELINE.md
  Include concrete findings, screenshots only if safe, and exact test commands.
- Add no visual changes in this phase.

Acceptance:
- Baseline report exists.
- No source behavior changes except optionally adding test/audit infrastructure.
- Existing typecheck/build and selected smoke tests have recorded outcomes.

PHASE 1 — INFORMATION ARCHITECTURE AND PAGE DENSITY
---
Goal: Reduce overload without removing features.

Tasks:
- Define a consistent page anatomy:
  1) context/breadcrumb,
  2) concise page title and one-sentence purpose,
  3) one primary action,
  4) primary content,
  5) optional details.
- Identify crowded Role Explorer and Assessment sections. Split them into
  purposeful sections or tabs; avoid one long unstructured scroll.
- Establish component hierarchy for cards:
  - Hero/primary action card: only one per view.
  - Standard content card: neutral and quiet.
  - Insight/status card: compact; never compete with the primary action.
  - Expandable detail panel: secondary evidence, explanations, raw metadata.
- Make alignment systematic: shared page rail, heading spacing, card padding,
  action placement, badge height, and consistent loading/empty/error spacing.
- Preserve all content. Move low-priority items behind an accessible Details
  expander, a tab, or a side drawer.
- Avoid “every card looks the same”: vary hierarchy through size, location, and
  purpose—not random gradients or decorations.

Acceptance:
- Roles and Assessments each have one obvious primary action above the fold.
- Page sections are visually grouped and labelled.
- No existing feature or route disappears.
- Test at 1440px, 1024px, 768px, and 390px widths in both main themes.

PHASE 2 — LEARNING PLAN AS A TRACKABLE JOURNEY
---
Goal: Make learning feel like a clear route rather than a list of content.

Desired learning page flow:
- “Continue your plan” hero: current lesson, estimated time, purpose, and one
  CTA: Continue learning.
- Path map: 5–8 visible milestones at a time. Each item shows one state:
  completed, current, upcoming, locked, or needs review.
- Lesson screen: Learn -> Example -> Practice -> Mini check, one active section
  at a time. The user can revisit completed sections.
- Plan details: optional drawer/tab for prerequisites, all lessons, resources,
  rationale, and deeper explanations.

Tasks:
- Build reusable components for milestone states, current lesson card, and
  lesson-section progression. Use actual lesson/path state from the backend.
- Clearly distinguish “progress through the plan” from “verified skill.” Never
  imply that reading a lesson verifies competence.
- Explain every score in plain language. Example: “50% role coverage means the
  system found evidence for half of this role’s listed requirements. It is not
  a hiring guarantee.”
- Add an unobtrusive “Why this?” link beside calculated coverage/match scores.
- Include useful empty states: no role selected, no diagnostic yet, no path yet,
  and no lessons available. Each has one action that resolves it.
- Do not create fake timers, streaks, completion claims, or AI-generated plans
  when the backend did not return them.

Backend requirements:
- Reuse existing path/lesson/progress endpoints where possible.
- If a new persisted field is necessary, add a safe migration and endpoint;
  return the field in existing relevant read responses; add backend tests.
- Do not calculate persistent progress only in React local state.

Acceptance:
- A student can see their single next action, resume it after refresh, navigate
  the plan, and understand all milestone states.
- Existing curated lessons retain their starter code, static-review messaging,
  and safe non-execution behavior.

PHASE 3 — ASSESSMENTS THAT FEEL FOCUSED, NOT INTIMIDATING
---
Goal: Make assessments simple before, during, and after completion.

Tasks:
- Assessment landing screen should show only: skills covered, approximate
  duration, question count if known, what the result changes, and Start.
- Assessment player should show one question at a time, clear progress (for
  example “3 of 10”), Back/Next, autosave only if the backend supports it, and
  an exit/return-later option.
- Results screen should contain:
  - a plain-language result headline,
  - strengths (maximum three),
  - improvement areas (maximum three),
  - one primary next action such as “Add this to my plan.”
- Put raw score breakdowns, rubric details, and evidence behind “View details.”
- Ensure assessment status is honestly derived from backend state. Do not label
  something passed/verified unless the current backend actually says so.

Backend requirements:
- Verify existing attempt/resume/status data before creating new storage.
- If adding autosave/resume, use explicit attempt states, ownership checks,
  authorization tests, idempotency, and recovery from page refresh.
- Add tests that prevent one student reading/modifying another student’s attempt.

Acceptance:
- One question is shown at once.
- Leaving and returning does not lose a supported in-progress answer.
- Results point to a real existing plan/lesson/action.

PHASE 4 — WELCOME TOUR AND CONTEXTUAL MINI-TOURS
---
Goal: Let new students understand SkillBridge without a tutorial wall.

Global welcome tour: maximum 5 short steps.
1. Dashboard: what “Next step” means.
2. Roles: choose the destination for the learning path.
3. Learning: diagnose gaps and follow a plan.
4. Practice/Assessments: practise safely and measure progress.
5. Mentor/Jobs: optional help and opportunity exploration.

Required controls:
- Next, Back, Skip tour, and “Don’t show again.”
- Never trap keyboard focus; Escape closes it.
- Reopen from Help/Settings as “Replay product tour.”
- Do not re-show automatically after the user skips or completes it, except
  after a major versioned tour update with a clear reason.

Contextual mini-tours:
- Roles: explain target role, requirement coverage, and Browse roles.
- Learning: explain diagnostic, plan states, and the next lesson.
- Assessments: explain attempt, result, and how results affect recommendations.

Backend requirements:
- Persist each user’s tour state server-side, scoped to the authenticated user.
- Suggested shape: product_tour_version, product_tour_state, and per-page
  mini-tour completion state. Use a migration, validated API contract, and
  authorization tests. Do not rely solely on localStorage.
- Use localStorage only as an optional UI cache; backend is source of truth.

Accessibility requirements:
- Proper dialog semantics, focus trap, focus return, visible focus indicator,
  and reduced-motion support.
- The tour must be fully usable by keyboard and screen reader.

Acceptance:
- New account sees the welcome tour once.
- Existing account does not unexpectedly see it.
- Skip/complete/replay states survive refresh and a new browser session.

PHASE 5 — AI MENTOR AS A USER-CONTROLLED COMPANION
---
Goal: Make the mentor useful without stealing the page.

Tasks:
- Default mentor behavior should be contextual but not obstructive.
- Add a clear collapse/hide control and a persistent compact launcher.
- Reopen state must be obvious and keyboard-accessible.
- On smaller screens, open mentor as a focused bottom sheet/drawer rather than
  permanently taking a third of the screen.
- Offer contextual prompts based on the current page, but never force the user
  into a chat flow. Examples: “Explain this score,” “Plan this lesson,” “Help
  me practise this concept.”
- Keep existing tutor safety, provider errors, voice quota errors, and offline
  fallback messages honest and visible.

Backend requirements:
- Persist mentor visibility/preference per user if the project already has a
  preference/settings model; otherwise add a minimal owned preference field.
- Do not alter chat authentication, provider keys, message history access, or
  voice behavior without separate tests.

Acceptance:
- The mentor can be hidden, reopened, and stays in the chosen state after
  refresh.
- It does not cover vital content or primary actions.
- It works with keyboard, mobile, light/dark, and Arabic layouts.

PHASE 6 — VISUAL DESIGN SYSTEM AND THEME POLISH
---
Goal: Make Professional and Casual Pulse feel intentional, premium, and calm.

Tasks:
- Consolidate spacing, radii, elevation, typography, page rail, focus, and
  color tokens in the current design-system/theme files. Do not scatter magic
  numbers through components.
- Professional Core: restrained color, high contrast, readable density, suited
  to university/recruiter contexts.
- Casual Pulse: dark navy/black base, restrained orange warmth, subtle blue
  highlights, expressive but not neon everywhere. Use accent sparingly for
  active state, progress, and primary action.
- Light variants must be designed, not merely inverted. Maintain readable
  contrast for muted labels, role titles, chips, and progress text.
- Ensure card labels inside circular progress indicators have enough room and
  never look stuck together. For narrow cards, use a stacked text layout rather
  than shrinking text until unreadable.
- Give role titles sufficient contrast; do not rely on dim secondary text.
- Add motion only for state transition, success, or navigation orientation.
  Respect prefers-reduced-motion.
- Keep logo assets and branding consistent; do not use copyrighted or copied
  TryHackMe/Hack The Box art.

Acceptance:
- Contrast and readability pass manually in every theme.
- No text overlap, clipping, or unreadable label at the required viewport sizes.
- Theme changes are immediate and persist using the project’s existing
  preference mechanism.

PHASE 7 — ACCESSIBILITY, RTL, RESPONSIVE, AND FAILURE STATES
---
Goal: Make polished behavior reliable for every student.

Tasks:
- Audit keyboard navigation, semantic headings, buttons, dialog labels, forms,
  visible focus, errors, loading states, and disabled controls.
- Test English LTR and Arabic RTL. Do not mirror code snippets or technical
  command order incorrectly in RTL.
- Test 1440px, 1024px, 768px, and 390px viewport widths.
- Prevent horizontal scroll, card overflow, clipped tooltips, hidden buttons,
  and content obscured by the mentor panel.
- Add clear error/loading/empty states for jobs, tutor, diagnostics, lessons,
  assessments, and network failures. Retry controls must call real actions.
- Preserve privacy: provider errors/log messages must never reveal keys,
  credentials, or raw internal diagnostics to students.

Acceptance:
- Core flows work with keyboard only.
- No layout overflow at specified sizes.
- Arabic and English pages remain readable and logically ordered.

PHASE 8 — QUALITY GUARDIAN AND FINAL EVIDENCE
---
Goal: Prevent visual and functional regression after the redesign.

Tasks:
- Extend existing browser regression harnesses instead of adding an unrelated
  test framework unless necessary.
- Create a page/viewport/theme matrix for Dashboard, Roles, Learning,
  Assessment, Settings, and mentor states.
- Add automated checks for:
  - broken routes and console errors,
  - key primary actions visible/enabled,
  - overflow and off-screen elements,
  - buttons covered by mentor/tour overlays,
  - selected-theme persistence,
  - onboarding completion/skip/replay persistence,
  - no cross-user preference or assessment access,
  - existing curated lesson/practice safety behavior.
- Capture before/after screenshots only from a local test instance. Do not
  include secrets, real CVs, private databases, or provider output in reports.
- Write docs/ux-upgrade/FINAL_UX_VERIFICATION.md containing changed files,
  tests, screenshot matrix, known limitations, and manual inspection checklist.
